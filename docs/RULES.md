## 1. ゲーム概要 ✅

Web制作会社のチームとして1つの案件を完遂する、**4〜5人協力型**ゲーム。
プレイヤーは「WBSを立て → 自分の役割を判断し → イベントを捌き → タスクをこなし → 責任を果たし →
お客様の成果に繋げる」を追体験します。

**主眼は教育です。** 勝ち筋の最適化そのものより、
「見積は外れる」「品質を落とすと後で返ってくる」「全部は約束できない」を身体で理解することが目的です。

- **だまし合いはありません。** 秘匿情報は個人目標のみ(v5.0 では未実装)
- **物理版で成立すること。** 隠し計算・連続値・複雑な同時解決を持ち込みません

### 勝敗条件 ✅

- 勝敗トラックは **CS(顧客満足度)1本**
- ゲーム中に **CS が 0 未満**になった時点で即時敗北
- 最終フェーズ終了時の**最終検収**を清算し、**CS ≥ 0 なら勝利**

### ゲームの規模 ✅

- **1ゲーム = 4フェーズ(企画 / 設計 / 開発 / テスト)**
- **1フェーズ = 3週**
- 各週、各プレイヤーは行動枠1つ(+条件付きで残業枠1つ)を使う

## 2. 通貨と盤面の基本 ✅

### 2-1. 工数キューブ(唯一の通貨)

タスクカードには次が刷ってあります:

**埋めるスロット / 系統(📋dir・🎨des・⚙eng のいずれか1つ)/ 見積工数 / リスク /
上限Lv / 疲労値(1 または 2)/ 実行コスト(予算)/ 前提成果物**

- プレイヤーがタスクに1週座ると、**その系統の自分のスキル値ぶん**のキューブを積みます(スキル0の系統には座れません)
- キューブは**タスクに残ります**。人は毎週手元に戻り、続けるか離れるかを選び直します(拘束なし)
- 複数人で座れば足し算。**同じ人が主担当+残業で同じタスクに2枠使うのも可**です

### 2-2. 見積工数と実工数(#3)✅

> 現実の「思ったより工数がかかった」をルールに入れます。

- カードに刷ってあるのは **見積工数** と **リスク(低 / 中 / 高)** です。**公開情報**です
- **実工数 = 見積工数 + 実工数補正**。補正はリスク別の分布からシード付き乱数で決まります
- 補正は伏せられており、**そのタスクに初めてキューブが積まれた週の週末に公開**されます
  (= 着手して初めて本当の重さが分かる)
- 公開後、必要工数・完了見込み・後続予定はその値で再計算されます

**実工数補正の分布** 🔧(`riskVariance`。等確率で1つ引く)

| リスク | 補正の分布 | 期待値 |
|---|---|---|
| 低 | 0 / 0 / +1 | +0.33 |
| 中 | -1 / 0 / +1 / +2 | +0.50 |
| 高 | 0 / +1 / +2 / +2 | +1.25 |

- 低リスクは振れ幅が小さく、高リスクは上振れします。**中リスクだけが下振れ(-1)を持ちます**
- 同じシードと同じアクション列なら、必ず同じ実工数になります(リプレイ再現性)
- 同じスロットを埋める手段が複数あるとき、「見積は短いが高リスク」「長いが低リスク」の
  **代替案としてコンテンツを用意します**

**必要工数の計算式**(盤上タスク1枚)

```
必要工数 = (実工数が公開済みなら実工数 / 未公開なら見積工数) + 🔥の数 - 恒久減(自動化など)
          ただし最低 1
```

### 2-3. 納品と品質(#5)✅

キューブが必要工数に達したタスクは、**週末に納品できます**(チームで選択):

- **そのまま納品** → スロットが **Lv1** で埋まる
- **積み増し続行** → さらに +`qualityOvershoot`(🔧 2)個積んでから納品すると **Lv2**
  (上限Lv1 のタスクは不可。必要工数+overshoot を超えては積めません)

納品時に**実行コスト(予算)を支払います**。予算が足りなければ納品できません(積んだキューブは残ります)。

**改修**:納品済みの Lv1 スロットには「改修」として座れます(系統=スロットの系統)。
+`upgradeCost`(🔧 3)個積むと Lv2 に上がります。

> 納品前に丁寧にやれば +2、納品後に直すと +3。**安物買いの銭失い = 技術的負債**の学びです。

### 2-4. 品質リスク(#5)✅

**Lv1 と Lv2 の意味を、点数ではなく「将来の不確実性」に接続します。**

- **Lv1**:最低限納品できるが、**品質リスクが残る**
- **Lv2**:レビュー・テスト・磨き込みまで完了し、**品質リスクがない**

ルール:

1. **Lv1 で納品したスロットには、品質リスクマーカーを置きます**(⚠)
2. **Lv2 で納品した場合、品質リスクは付きません**
3. 改修で Lv2 に上がったとき、個人能力「磨き込み」で Lv2 にしたとき、品質リスクは**除去されます**
4. **手戻り・バグ報告の対象選択は、品質リスクのあるスロットを優先します**
   (品質リスクのあるスロットが1つ以上あれば、その中からシード乱数で選ぶ。無ければ納品済み全体から選ぶ)
5. **品質リスクのあるスロットへの手戻り対応は、必要工数 +`qualityRiskEffortPenalty`(🔧 1)** です
6. 品質リスクそれ自体にフェーズ末の CS ペナルティはありません
   (最終検収の Lv 不足罰と二重に罰さないため)。**代わりに「狙われやすさ」と「対応工数」で効きます**
7. 一部のイベントカードは「品質リスクのあるスロットがあれば CS-1」を効果に持ちます(コンテンツ側で表現)

> **急いで Lv1 で納めて先に進む**判断と、**Lv2 まで待って安全を買う**判断が、どちらも成立します。

### 2-5. 🔥(炎上)✅

- 🔥1個 = そのタスクの必要工数 +1(スコープクリープ)。**未納品のタスクにのみ乗り**、納品すると消えます
- 炎上カードの対象は**名指しではなく条件式**です(§9 参照)。同数・複数該当は PM 帽子が裁定します
- **延焼**:同一タスクの🔥が `fireOutbreakThreshold`(🔧 3)個目に達したら、置く代わりに
  **同じ予定週のタスク全部に🔥+1、CS-1**
- **大炎上**:進行中の全タスクに🔥+1
- **消火**(週アクション):任意のタスクの🔥1個を除去。**系統・スキル不問**(誰でもできる)

### 2-6. 疲労(0〜4 の数値トラック)✅

- タスク/改修に座った週:+タスクの疲労値(1 or 2)。残業:さらに +1(即時)
- **疲労 2 以上:残業禁止**
- **疲労 4 到達:限界イベント**(カードを1枚引いて解決し、疲労 `limitResetFatigue`(🔧 2)に戻る)
- 休憩(週アクション):-2。フェーズ末:全員 -1

## 3. スコープ管理 — Must / Better / 見送り(#1)✅

> **v4 の「約束」は廃止しました。**
> 未達に罰があるだけで達成報酬がなく、「約束しないほうが有利」になっていたためです。
> また実務のスコープは固定的な約束ではなく、優先度・期限・交渉で変わります。

### 3-1. 要件カード

フェーズ開始時に、そのフェーズの**要件カード**が公開されます。**公開は累積**します(過去の要件も場に残ります)。

各要件カードは次を持ちます:

| 項目 | 内容 |
|---|---|
| 対象成果物 | プロダクトボードのスロット1つ |
| 要求品質 | Lv1 または Lv2 |
| 期限 | フェーズ番号(このフェーズ末に清算) |
| 初期区分 | **Must** または **Better**(カードに刷ってある) |

### 3-2. 3つの区分 ✅

| 区分 | 意味 | 期限までに達成 | 期限までに未達 |
|---|---|---|---|
| **Must** | 期限までに必要 | **CS +0**(期待値どおり)| **CS -`mustMissCs`**(🔧 2)|
| **Better** | 任意。やれば喜ばれる | **CS +`betterMeetCs`**(🔧 1)| **CS ±0**(罰なし)|
| **見送り** | 今回のスコープ外 | — | **CS ±0** |

- **Must 単体の達成は基本期待値**であり、それ自体では CS は増えません(未達回避の価値があります)
- ただし §4-2 の**信頼ボーナス**があります
- **Better を見送っても罰はありません。CS 獲得の機会を失うだけです**

### 3-3. 達成の判定 ✅

要件が「達成」なのは、次をすべて満たすときです:

1. 対象スロットが **要求 Lv 以上**で納品されている
2. そのスロットを対象とする**手戻りカードが場に無い**

達成はその瞬間に確定し、**一度達成した要件は以後 CS を再獲得しません**(§4-3)。
ただし手戻りが乗ると、清算前であれば**未達成に戻ります**。

### 3-4. 期限とフェーズ末の清算 ✅

**期限フェーズの末に、要件を1回だけ清算します。**

- **Must・未達** → CS -`mustMissCs`。清算後、その要件は **未達確定(failed)** になり、以後フェーズ末の罰は繰り返しません
- **Must・達成済** → CS ±0
- **Better・達成済** → CS +`betterMeetCs`(未清算のぶんのみ)
- **Better・未達** → CS ±0。清算後 **失効(expired)** になります
- **見送り** → 清算対象外

> 未達を毎フェーズ繰り返し罰する構造(v4 の約束)はやめました。**1回の清算で完結**します。
> 未達確定・失効になった要件も、**最終検収(§4-4)では改めて評価されます。**

### 3-5. PM のスコープ交渉 ✅

PM 帽子のプレイヤーは、**いつでも**次のスコープ変更を行えます。
**Must を緩める変更にはコストがかかり、フェーズあたり `scopeChangePerPhase`(🔧 2)回までです。**

| 変更 | コスト | 回数消費 |
|---|---|---|
| Must → Better 化 | CS -`demoteMustCs`(🔧 1)| ✅ |
| Must → 見送り | CS -`dropMustCs`(🔧 2)| ✅ |
| 期限を +1 フェーズ延長(Must のみ)| 予算 -`extendDeadlineBudget`(🔧 3)| ✅ |
| Better → Must 化 | なし | — |
| Better → 見送り | なし | — |
| 見送り → Better / Must | なし | — |

- 清算済み(未達確定・失効)・達成済の要件は変更できません
- 期限延長は**最終フェーズを超えては設定できません**
- 自分でスコープを厳しくする方向(Better → Must、見送り → Must)は無料です

### 3-6. 追加要望 ✅

イベントによる追加要望は、**新しい要件カードとしてスコープボードに入ります**(§7-3 `ADD_REQUIREMENT`)。
入るときの区分・期限はイベントの選択肢が決めます。入ったあとは通常の要件と同じく §3-5 で交渉できます。

## 4. CS の増減(#8)✅

> v4 の CS は「失敗を受け止める耐久値」に偏っていました。
> **仕事の成果で能動的に上げる経路**を用意します。

### 4-1. CS が増える経路 ✅

| 経路 | 量 | 重複防止 |
|---|---|---|
| **Better 要件の達成**(期限フェーズ末に清算)| +`betterMeetCs`(🔧 1)| 要件1枚につき1回 |
| **信頼ボーナス**:その期限フェーズの Must を**すべて**達成 | +`allMustBonusCs`(🔧 1)| フェーズ1回。Must が1枚以上あるフェーズのみ |
| **イベントの追加対応**:選択肢で受け、条件を達成 | カード定義(🔧 通常 +1)| イベント1枚につき1回 |
| 一部のイベント効果(褒められた 等)| カード定義 | — |

### 4-2. 信頼ボーナス ✅

期限フェーズの清算時、**そのフェーズを期限とする Must がすべて達成されていたら CS +`allMustBonusCs`**。
Must が0枚のフェーズには発生しません。

> 「Must は達成して当たり前」を保ったまま、**全部きっちり守ったチームには信頼が積まれる**、を表現します。

### 4-3. 重複獲得の防止 ✅

同じ要件・同じイベントから CS を2回獲得することはできません。
エンジンは獲得済み ID(`csAwardedRequirementIds` / `csAwardedEventIds`)を状態に保持します。

### 4-4. 最終検収 ✅

最終フェーズの終了時、**公開されたすべての要件**(見送り・未達確定・失効を含む)を改めて清算します。

| 状態 | CS |
|---|---|
| 要求 Lv を満たしている(手戻りなし)| ±0 |
| Lv2 要求を Lv1 で充足している | -`finalCompromiseCs`(🔧 1)|
| 未達成(未納品 or 手戻り中)| -`finalMissCs`(🔧 2)|

- 見送りにした要件も**最終検収では評価されます**(「今回はやらない」と決めたことの結果は最後に出ます)
- 清算後 **CS ≥ 0 なら勝利**

### 4-5. CS 増減の可視化 ✅

CS が動いたときは必ずログに理由を書きます(`💚 +1 …` / `💢 -2 …`)。
UI は現在の CS と直近の増減理由を常時表示します(§10)。

## 5. ローリング計画ボード(#2)✅

> v4 の WBS(起点・中盤・仕上げの固定列)は廃止しました。
> 工程の順序は**依存関係(§6)**が担い、時期の組み立ては**計画ボード**が担います。

### 5-1. 計画ボードの構造 ✅

```
[ Backlog ] [ 第1週 ] [ 第2週 ] [ 第3週 ] [ 見送り ]
```

- フェーズ開始時、チームは要件を実現する**タスク候補**を選び、**3週間のいずれかへ配置**します
- **Backlog** はやると決めたが週を決めていないタスク。**見送り**は今フェーズではやらないタスク(場から外れます)
- タスクカードは常時 `draftPool`(🔧 8)枚が候補として場に並びます(補充はスコープ会議時のみ)

### 5-2. 予定工数と供給能力の表示 ✅

各週について、**系統別の予定工数**と**チームの供給能力**を表示します。

```
第1週  📋 予定5 / 能力5      🎨 予定4 / 能力3 ⚠過負荷      ⚙ 予定2 / 能力4
```

- **予定工数** = その週に配置されたタスクの必要工数の合計(系統別)
- **供給能力** = その週に働ける全プレイヤーのその系統スキル値の合計
  (キャパシティ減 §7-3 を反映。残業枠は不確定なので数えません)
- **過負荷は警告するだけで、配置は許可します**(無理な計画を立てる自由があり、その結果が翌週に出ます)

### 5-3. 週の実行と計画の関係 ✅

- **朝会で座れるのは、`今週` に予定されたタスク・割り込みレーンのカード・改修だけ**です
  (Backlog や来週予定のタスクには座れません)
- **計画の変更(再計画)ができるのは、スコープ会議中と週末だけ**です
  → 「今週やること」は朝会の時点で確定しており、**計画を立てたこと自体に意味があります**

### 5-4. 週末の再計画 ✅

週末(納品判定のあと、次週に移る前)に、チームは自由に再計画できます:

- タスクの予定週を移動する(Backlog ⇄ 各週)
- タスクを見送りにする(場から外す。積んだキューブは失われます)
- 候補プールから新しいタスクを取って配置する

**未完了タスクの自動繰越**:週を締めるとき、予定週が過ぎているのに未完了のタスクは
**自動的に翌週へ繰り越されます**(ログに記録)。フェーズ最終週を過ぎたものは Backlog に戻ります。

> 自動確定はしません。繰越はあくまで既定値で、**移動・見送りはチームが週末に決めます**。

## 6. 依存関係と遅延の伝播(#4)✅

> v4 の「起点・中盤・仕上げ」は配置時の文法にとどまり、実行時にはほぼ機能していませんでした。
> **先行タスクの遅れが後続の開始をずらす**体験を作ります。

### 6-1. 前提成果物 ✅

タスクカードは **前提成果物(`prerequisiteSlots`)** を持ちます(0個〜複数)。

- 前提スロットが**すべて納品済み(Lv1 以上)** かつ **手戻り中でない**とき、そのタスクは着手可能です
- ひとつでも満たさないタスクは **「ブロック中」** です

### 6-2. ブロック中の扱い ✅

- ブロック中タスクは盤面で明示されます(🔒)
- **ブロック中タスクには朝会でワーカーを配置できません**(エンジンが `TASK_BLOCKED` で拒否します)
- **計画ボードへの配置は自由です**(先を見越して第3週に置くのは正しい計画です)
- 前提が満たされた瞬間からブロックは外れます(週の途中でも、その週末の納品で外れれば翌週から着手可)

### 6-3. 遅延の伝播 ✅

- 先行タスクが見積を超えて終わらなければ、それを前提とする後続タスクは**ブロックされたまま**になります
- 週末に、**「ブロック中のまま予定週を迎える/過ぎた」タスクは影響ありとして強調表示**されます
- 繰越は §5-4 のとおり自動、**移動・見送りの判断はチームが再計画で行います**
- **同一週内で先行・後続を同時に完了させる前提にはしません**(納品判定は週末に1回だけのため、
  先行の納品が確定するのは週末。後続の着手は最短でも翌週です)

## 7. イベント — 週末に起き、次週を崩す(#6)✅

> v4 は週初に炎上・イベントをすべて見てからワーカーを置くため、
> 「既知の問題に最適配置する」だけの流れでした。**外部からの変化は週末に来ます。**

### 7-1. タイミング ✅

| 時点 | 起きること |
|---|---|
| **週初** | 🔥炎上カードを `firePerRound`(🔧 1)枚めくって解決(内部の乱れは週の頭に見える)|
| **朝会** | 配属(§8)|
| **週末** | 納品判定 → **イベントカードを1枚めくって解決** → 再計画 → 次週へ |

イベントの結果は**次週の計画に効きます**。だから週末の再計画(§5-4)がイベントの直後に来ます。

### 7-2. 選択肢 ✅

主要なイベントには **2つ以上の選択肢**があります。選ばなかった道の値打ちが判断を作ります。

| 選択 | 典型的な内容 |
|---|---|
| **受ける** | スコープや割り込みが増える。達成すると CS +1 |
| **交渉する** | 予算または CS を払って、期限・工数・優先度を有利にする |
| **断る** | CS が減る、または機会(CS 獲得や予算)を失う |

- 選択肢のないイベント(単純な予算増減など)は、そのまま解決します
- **選択と結果はアクションログに残り、リプレイで再現できます**(`RESOLVE_EVENT` に `choiceId` を含めます)

### 7-3. イベント効果の種類 ✅

| 効果 | 内容 |
|---|---|
| `BUDGET` / `CS` / `FATIGUE_ALL` | 予算・CS・全員の疲労を増減 |
| `INTERRUPT` | 割り込みレーンにカードを追加(§8-4)|
| `CAPACITY_DOWN` | **他案件ヘルプ**:対象プレイヤーの**次週**に積むキューブを -`capacityDownCubes`(🔧 1)|
| `BLOCK_TASK` | **クライアント確認待ち**:対象タスクを**次週は開始できない**(1週だけのブロック)|
| `ADD_REQUIREMENT` | **要件追加**:新しい Must / Better をスコープボードへ(§3-6)|
| `QUALITY_AUDIT` | **品質レビュー**:品質リスクのあるスロット1つにつき CS -1(上限はカード定義)|
| `NONE` | 何も起きない |

対象プレイヤー・対象タスクは**シード付き乱数**で選びます(再現可能)。

### 7-4. 代表イベント ✅

| カード | 選択肢 |
|---|---|
| 他案件ヘルプ | 受ける(キャパ減・CS+1 の機会)/ 断る(CS-1)|
| クライアント確認待ち | 待つ(対象タスクが次週ブロック)/ 押し切る(CS-1、ブロックなし)|
| 要件追加 | Must として受ける(CS+1 の機会)/ Better として受ける / 断る(CS-1)|
| 仕様変更 | 受ける(納品済みスロットへ手戻り)/ 交渉(予算-3 で回避)|
| バグ報告 | 対応する(⚙ 必須の割り込み)/ 様子を見る(次フェーズ末まで CS 出血)|

## 8. 週の進行 ✅

### 8-1. スコープ会議(フェーズ開始)✅

1. そのフェーズの**要件カード**を公開する(累積。§3-1)
2. チームで **Must / Better / 見送り** を確認し、必要なら PM が交渉する(§3-5)
3. **タスク候補**を場に補充し(`draftPool` 枚)、やると決めたタスクを**計画ボードの週へ配置**する(§5-1)
4. PM が会議を締めて第1週へ

> 要件の総需要はチームの供給より常に大きく設計します。**全部は Must にできません。**

### 8-2. 週初 ✅

炎上カードを `firePerRound` 枚めくって解決します(§2-5)。

### 8-3. 朝会(同時配置)✅

各自が「今週の自分」を1つ決めます:

- **座る**:今週予定のタスク / 割り込みレーンのカード / 改修(Lv1 スロット)。自分のスキルぶん積む
- **学習**:系統を選びスキル +1(**反映は来週から**。上限 `skillMax`(🔧 3))
- **休憩**:疲労 -`restRecovery`(🔧 2)
- **消火**:🔥1個除去

任意で **残業**:+1枠(**座る / 消火のみ**)。即時疲労 +1。疲労 `noOvertimeAtFatigue`(🔧 2)以上は不可。

**配属の制約:**

| 制約 | 理由 |
|---|---|
| スキル0の系統には座れない | §2-1 |
| ブロック中タスクには座れない | §6-2 |
| 今週予定でないタスクには座れない | §5-3 |
| 全員が配属を決めるまで準備完了できない | §10(未配属 Ready の防止)|

**個人能力**(§9-2)は行動枠を消費しません(フリーアクション。フェーズ1回)。

### 8-4. 割り込みレーンと専門スキル(#7)✅

イベントの差し込みは**すべてカードとして割り込みレーンに置かれます**。

**割り込みカードは必要スキルを持ちます。**

| 差し込み | 必要スキル |
|---|---|
| 顧客確認・要件変更 | 📋 ディレクション |
| デザイン手戻り | 🎨 デザイン |
| バグ・障害 | ⚙ エンジニアリング |
| 一般相談 | 指定なし(最高スキルで対応)|
| 手戻り(スロット由来)| **対象スロットの系統** |

> これにより、**計画タスクと突発対応で同じ専門家を取り合う**状況が生まれます。
> 「今週このデザイナーをどっちに置くか」が毎週の判断になります。

**種別ごとの放置コスト**(トリアージの根拠):

| 種別 | 放置すると |
|---|---|
| **手戻り** | 対象スロットは**検収上「未達」扱い**(要件を塞ぐ)。積み切れば解消し Lv は元に戻る |
| **バグ報告** | **フェーズ末ごとに CS -1**(出血が続く)|
| **相談ごと** | **フェーズ末に自然消滅**(罰なし)。ただし場にある間は枠を塞ぐ |

**キャパシティ**:割り込みレーンの枠は `interruptCapacity`(🔧 4)。
満杯のところへ新しい差し込みが来たら**置けず、即 CS -`overflowCs`(🔧 2)**、カードは捨て札になります。

**謝絶**(PM・回数無制限):割り込みレーンのカード1枚を取り下げ、即時 CS -`declineCs`(🔧 1)。
**あふれ(-2)より安く、選んで断れます。断る勇気はルールで報われます。**

### 8-5. 週末 ✅

1. 配属の効果を一括適用(残業疲労 → 休憩 → 学習予約 → 消火 → キューブ → 着席疲労)
2. **初めてキューブが積まれたタスクの実工数を公開**(§2-2)
3. 必要工数に達したタスクの**納品判定**(§2-3)。納品したスロットの品質リスクを更新(§2-4)
4. **イベントカードを1枚解決**(§7)
5. **再計画**(§5-4)
6. 週を締める → 次週へ(最終週ならフェーズ終了へ)

### 8-6. フェーズ終了 ✅

1. **要件の清算**(§3-4):期限がこのフェーズの Must / Better を1回だけ清算
2. **信頼ボーナス**(§4-2)
3. 相談ごとの期限切れ(自然消滅)
4. **バグ放置の出血**(CS -1 / 件)
5. 疲労の自然回復(全員 -`phaseEndRecovery`(🔧 1))
6. **キャパシティ減・一時ブロックのクリア**
7. 次フェーズのスコープ会議へ。最終フェーズなら**最終検収**(§4-4)

## 9. メンバーと PM 帽子 ✅

職業クラス制はありません。**能力(メンバーカード)**と**責任(PM 帽子)**を分離します。

### 9-1. メンバーカード ✅

各プレイヤーに1枚。**スキルプロファイル + 個人能力 + 経歴フレーバー**を持ちます。

| 例 | 📋dir | 🎨des | ⚙eng | 個人能力(フェーズ1回・行動枠を使わない)|
|---|---|---|---|---|
| 元エンジニアの何でも屋 | 1 | 1 | 1 | **マルチタスク**(パッシブ):残業の追加疲労なし |
| デザイン寄り | 1 | 2 | 0 | **磨き込み**:週末に、納品済みスロット1つを Lv1→Lv2(品質リスクも除去)|
| マネジメント寄り | 2 | 1 | 0 | **段取り**:朝会で宣言。今週自分の積むキューブ +1 |
| 開発寄り | 0 | 1 | 2 | **自動化**:未納品タスク1つの必要工数 -1(いつでも)|

- スキル 0 の系統には座れません。1 あれば座れます(**遅くても手伝える**)
- スキルは学習で育ちます(上限 `skillMax`)
- 5人プレイはカードを1枚増やすだけです

### 9-2. PM 帽子 ✅

**PM マーカー**を1人が被ります(セットアップで決定)。権限:

- **スコープ会議の最終決定**(要件区分・計画ボード配置)
- **スコープ交渉**(§3-5):Must の格下げ・見送り・期限延長。フェーズ `scopeChangePerPhase` 回まで
- **候補の引き直し**(スコープ会議中・フェーズ1回):タスク候補2枚まで引き直す
- **謝絶**(§8-4・回数無制限)
- **追加請求**(フェーズ `extraBillingPerPhase`(🔧 1)回:CS -1 で予算 +`extraBillingBudget`(🔧 3))
- **裁定**:炎上対象の同数タイブレークなど、ルールが指定しない選択
- **週末を締める**

スキルと責任は独立しているので、「PM 寄りスキルの人が帽子を被るとは限らない」も起きます(実務どおり)。

### 9-3. 炎上カードのターゲット条件 ✅

| 条件 | 内容 |
|---|---|
| `most_cubes` | キューブ最多の未納品タスク |
| `oldest` | 最も古く場に出た未納品タスク |
| `this_week` | 今週予定のタスク(なければ最も近い予定週)|
| `blocked` | ブロック中のタスク(なければ最も古いタスク)|
| `epidemic` | 大炎上:進行中の全タスクに🔥+1 |

複数該当は配置順で先のもの(物理版は PM 裁定)。

## 10. 盤面と操作の情報設計(#9)✅

デジタル版は「卓のシミュレーション」ですが、**読めること・押せること**を物理版より優先します。

### 10-1. 操作 ✅

- **クリック配置を標準操作とします**:ミープルを選択 → 配置可能な場所が発光 → 配置先をクリック
- **ドラッグも併用できます**。ドラッグ中は**カード全体**が有効なドロップ領域です
- マウス・タッチの双方で全操作が完了できること

### 10-2. 予告(プレビュー)✅

配置を確定する前に、その配置の結果を数値で見せます:

- **進捗**:このタスクのキューブが `4 → 6 / 必要7` になる
- **疲労**:`1 → 3`(残業なら +1 も含む)
- **納品見込み**:今週末に Lv1 納品可 / あと2人日 / Lv2 には +2
- **予算影響**:納品したら予算 `12 → 10`

### 10-3. 固定 HUD ✅

ズームしても常に画面内に固定されるもの:

- CS・予算・フェーズ・週
- **今週の目標**:期限が近い Must / 達成候補の Better / 未対応の割り込み
- 進行ボタン(準備完了・週末を締める など)
- 選択中プレイヤーの残り行動・得意スキル

### 10-4. 表示ルール ✅

- **内部 ID(`sitemap`・`requirements` 等)は画面に出しません**。必ず日本語の表示名を使います
- 100% 表示で主要カードの本文が読めること(全体縮小のデフォルトをやめる)
- 自分のミープルを強調する
- **未配属のまま準備完了できません**
- **全員が確定するまでは準備完了を解除できます**
- 初期設定(GameConfig)は「詳細設定」に収納し、通常は見せません

### 13-1. 達成した基準 ✅

- **① 極端戦略は支配的にならない。** 「全部見送り」は勝率 0%(Must 1件の見送りが CS-2、
  さらに最終検収で -2 と二重に効く)
- **② 成り行きは最強ではない。** v4.1 では「成り行き」が全設定で最強だったが、
  v5 では triage(66.0%)> driftAlong(60.2%)で逆転した。
  **#8 の Better 達成・信頼ボーナスは効いている**(信頼ボーナス 平均 2.4 回/ゲーム、
  Better 達成率 51〜63%)。この逆転は依存の形・流入・需要をどう振っても崩れなかった
- **⑥ 勝率は振り切れていない**(混合 35.0%、最高 66.0%)
- **見積差異(#3)は意図どおり効いている。** 上振れは平均 2.8〜5.3 人日/ゲーム。
  安い道(高リスク)を選ぶ戦略ほど上振れが大きい

### 13-2. 未達の基準と原因 ❌

**③ 謝絶が使われない(目標 差し込みの1〜3割 → 実測 0.0〜0.2%)**

あふれは **0.00件/ゲーム**。`interruptCapacity` を 4 → 1 に絞っても 0.31件/ゲームにしかならず、
謝絶率は動きませんでした。原因は枠の広さではなく、**チームに手空きがあること**です
(手空き率 9〜19%。余剰は約15人日/ゲーム、割り込みの総量は 4〜12人日)。
余っている手で無料で吸収できるので、CS-1 を払う謝絶は常に損になります
(`declineHeavy` は全条件で下位)。

→ **`interruptCapacity` の調整では直りません。** 割り込みが「手空きでは吸収できない」
量・質になるか、余剰能力そのものが減る必要があります。

**④ デススパイラルが多い(目標 <20% → 実測 最大 44.2%)**

Must 達成率が 66〜70%(4件中およそ1.2件を落とす)で、`mustMissCs`=2 に初期 CS 5 では
途中敗北が積み上がります。ただし **`mustMissCs` を 1 に下げると ② が壊れます**
(driftAlong が 70.0% で最強タイになる)。この2つはトレードオフの関係にあります。

**⑤ 仕事がない週がある(目標 <10% → 実測 10.6〜16.8%)**

前提成果物が**ほぼ一本の直列チェーン**(要件定義 → サイトマップ → ワイヤー →
デザインカンプ → トップ → 公開)で、納品判定は週末に1回だけ(§6-3)。
つまり **1週にチェーンを1段しか進められず**、4人の並列性が吸収されません。
依存を並列寄りに組み替えた検証では、仕事がない週が 11.3% → 8.7% に下がり基準を満たしました。

### 13-3. 最大の発見:ルールの意図と数値が逆を向いている ⚠️

**「早く Lv1 で出して、後から改修する」戦略が全条件で最強です。**

| | Lv1比率 | 勝率 |
|---|---|---|
| triage(即納品)| 96.9% | **66.0%** |
| driftAlong(即納品)| 93.7% | 60.2% |
| balanced(要件どおりの品質)| 81.4% | 31.6% |
| betterChaser(Lv2 を狙う)| 81.3% | 28.2% |

Lv2 を待つ戦略は勝率がおよそ**半分**になります。理由は、
**Lv2 待ちの遅延が後続タスクをブロックし続ける**ことで、その損失が
`finalCompromiseCs`(1)と品質リスクの実害を大きく上回るためです。
triage は品質リスクを 3.5 スロット残したまま勝ちます。

§2-3 は「納品前に丁寧にやれば +2、納品後に直すと +3。**安物買いの銭失い**」を
教えるつもりで書かれていますが、現在の数値は逆に
「**早く出して後で直せ**」を教えています。品質リスク(§2-4)にフェーズ末の罰を置かなかった
判断(§2-4-6)が、低流入と相まって効いていません。

### 13-4. 検討中の対策(未適用。プレイテストと合わせて判断する)❓

| 課題 | 案 | 副作用の懸念 |
|---|---|---|
| ③ 謝絶が無意味 | 割り込みの必要工数を 2 → 3〜4 に上げ、手空きで吸収できなくする | v4.1 では「工数の可変化で全体難度が崩壊」した前例あり |
| ③ 同上 | 割り込みを放置したときの出血を強める(バグの CS-1/フェーズ末 → 週ごと)| デススパイラルを悪化させる |
| ⑤ 直列チェーン | 前提成果物を並列寄りに組み替える(デザインと実装を分岐させる)| #4 の「遅延が後続に伝播する」体験が薄まる |
| 13-3 Lv2 の価値 | `qualityOvershoot` を 2 → 1 に下げ、Lv2 を安くする | Lv2 が常に正解になり選択が消えるおそれ |
| 13-3 同上 | 品質リスクにフェーズ末の小さな罰を戻す(§2-4-6 の再検討)| 最終検収の Lv 罰と二重になる |
| ④ 途中敗北 | 初期 CS を 5 → 6〜7 に上げる | ② とのトレードオフは残る |

**いずれも未適用です。** どれもゲームの狙い(§1 の教育目標)に関わる判断なので、
数値だけで決めず人間のプレイテストと合わせて確定します。

### 13-5. シミュレータの使い方

```bash
pnpm --filter @smart-project/engine sim                          # 既定設定 × 全戦略
pnpm --filter @smart-project/engine sim -- --games 500           # ゲーム数
pnpm --filter @smart-project/engine sim -- --sweep mustMissCs=1,2,3
pnpm --filter @smart-project/engine sim -- --inflow experience,triage,pressure
pnpm --filter @smart-project/engine sim -- --demand base,high    # 要件の総量
pnpm --filter @smart-project/engine sim -- --deps serial,wide    # 依存グラフの形
pnpm --filter @smart-project/engine sim -- --json out.json       # 生データ
```

`--inflow` / `--demand` / `--deps` は**シミュレーション専用のコンテンツ差し替え**です
(エンジンの公開 API は変えていません)。製品に入れるならコンテンツ側の作業になります。

## 14. 未決事項(❓ 実装しない / パラメータで逃がす)

- ❓ **クライアントの個性**:QCD 重みに代わり「要件の構成・差し込みデッキの傾向」で表現する案。v5.1
